# compose-note

사용자가 이미 확보한 소스 자료(지금 대화 맥락 / 붙여넣은 텍스트 / 기존 메모)를 바탕으로 학습 노트 1개를 **뼈대~용어 보강까지 한 사이클로** 완성한다. `/new-note`·`/polish-note`·`/add-terms`를 개별 호출하는 수고를 없앤다.

## 입력
- 인자 `$ARGUMENTS`:
  - 카테고리 경로 (예: `개발/배포`)
  - 제목 (예: `GitHub Pages 배포 구조`)
- 소스 자료는 **별도로 전달하지 않는다**. 호출 시점의 대화 맥락, 또는 사용자가 커맨드 호출 전후로 붙여넣은 텍스트를 그대로 사용한다.

## 실행 순서

1. **소스 자료 확인**
   - 대화 맥락에 노트화할 내용이 충분한지 점검.
   - 부족하면 "어느 부분을 소스로 쓸지" 사용자에게 1회 확인.

2. **뼈대 생성 — `/new-note` 스킬 호출**
   - 카테고리·제목 전달. frontmatter·파일명·index.md 링크 자동 처리됨.
   - 반환된 파일 경로 기억.

3. **내용 채우기 (직접 편집)**
   - 소스 자료를 아래 표준 흐름에 재배치해서 채운다. **스킬 호출 아님 — Edit/Write로 직접 작성.**
     - **0. 개요**: 한 줄 요약
     - **1. 전체 개념/흐름**:
       - **1-1. 큰 그림**: 다이어그램·파이프라인 (ASCII 아트)
       - **1-2. 사전 지식/용어**: 본문 이해에 필요한 배경 (독자가 모를 수 있는 것만)
       - **1-3. 비교 예시**: 독자가 이미 아는 도구·개념과의 대조 표 — **1-4보다 반드시 먼저**
       - **1-4. 구성요소 역할**: 각 구성요소의 역할·수명 표
     - **2. 전체 예시 코드**: 돌아가는 완성품 (파일 전문, 명령어 시퀀스)
     - **3. 라인별 해설**: 용어·플래그·환경변수 단위로 bullet 해설
     - **4. 경험과 교훈**: 실패 사례·원인·해결 (소스 자료에 있으면)
     - **5. Best Practices**: 관례·함정 회피 (소스 자료에 있으면)
   - **비교 우선 원칙**: 1-3(비교) → 1-4(상세) 순서 고정. 비교가 설명보다 이해가 빠르다.
   - 문체는 처음부터 **간결체**(`~이다`, 명사형)로 작성. **주어 생략 지양.**
   - 소스 자료에 없는 사실은 **추정 금지**. `(작성 필요)` 플레이스홀더.
   - 불필요한 섹션(1-2·1-3·1-4·4·5)은 남기지 말고 삭제.

4. **문체·구조 점검 — `/polish-note` 로직 적용**
   - 이미 간결체로 썼다면 "문체 OK" 보고하고 구조만 재확인.
   - 섹션 순서가 6단 흐름에 어긋나면 재배치.
   - 깨진 `[[wikilink]]`가 있으면 경고만 출력 (자동 생성 금지).

5. **용어 보강 — `/add-terms` 스킬 호출**
   - 본문에 코드블록이 하나라도 있으면 호출.
   - 코드블록이 없으면 스킵하고 스킵 사유 보고.

6. **완료 보고**
   - 생성 경로 (markdown 링크).
   - 채운 섹션 / 비워둔 섹션(`(작성 필요)`) 목록.
   - 다음 추천 단계 (예: `/review-note`로 품질 체크).

## 금지
- 소스 자료에 없는 사실을 "추정"으로 채우지 않는다. 모르면 `(작성 필요)`.
- `quartz/`, `public/` 접근 금지.
- 코드블록 내부 내용은 사용자 원본 유지. 해설만 주변에 추가.

## 사용 예
```
/compose-note 개발/배포 GitHub Pages 배포 구조
```
→ 대화 맥락에서 `deploy.yml`·GitHub Actions·VM·OIDC 설명을 추출해 `content/개발/배포/1. GitHub Pages 배포 구조.md` 생성, 내용 채움, 문체·용어 점검까지 한 번에 수행.
