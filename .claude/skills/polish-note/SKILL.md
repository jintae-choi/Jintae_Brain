# polish-note

기존 노트를 표준 흐름에 맞춰 재구성한다.

## 레퍼런스
- 이상적인 구조 예시: `content/개발/git/6. git-hooks.md`, `content/개발/배포/1. GitHub Pages 배포 구조.md`
- 템플릿 기준: `content/templates/기본 문서 템플릿.md`

## 표준 흐름

```
0. 개요 (한 줄)
1. 전체 개념 / 흐름
   1-1. 큰 그림 (다이어그램)
   1-2. 사전 지식 / 용어
   1-3. 비교 예시 (익숙한 것과 대조) ← 1-4보다 먼저
   1-4. 구성요소 역할
2. 전체 예시 코드
3. 라인별 해설
4. 경험과 교훈
5. Best Practices
```

**비교 우선 원칙**: 1-3(비교)은 1-4(구성요소 상세)보다 반드시 먼저. 독자가 아는 것과의 대조가 이해를 빠르게 한다.

## 입력
- 대상 파일 경로 1개 (또는 현재 에디터 선택)

## 실행 순서

1. **현재 구조 분석**:
   - 섹션 제목 목록 추출
   - frontmatter 누락 필드 확인 (title, tags, date)
   - 서술형 종결(`~습니다`, `~합니다`) 카운트
   - 주어 생략 패턴 검출
   - 1-3(비교)과 1-4(구성요소) 순서가 반대로 되어 있는지 점검
2. **진단 보고** (2-5줄):
   - 현재 흐름이 표준 단계 중 어느 곳에서 어긋났는지
   - frontmatter / 문체 / 주어 생략 이슈
   - 재구성 플랜 요약
3. **사용자 승인** 후 재작성:
   - 기존 내용을 표준 섹션에 재배치 (내용 삭제 금지, 재배치만)
   - 1-3 → 1-4 순서 강제
   - 부족한 섹션은 `(작성 필요)` 플레이스홀더로 표시
   - 간결체로 통일 — `~습니다` → `~이다`, `~합니다` → `~한다`
   - 주어 생략된 문장에 주어 보강
   - 코드블록은 원본 유지
4. **wikilink 검증** — `[[...]]` 링크가 실제 파일과 일치하는지 Glob으로 확인. 깨진 링크는 경고만.

## 금지
- 내용(지식) 자체를 임의 추가·삭제하지 않는다. **재구성과 문체만** 수정한다.
- 원본 코드블록 내용을 변경하지 않는다.
- 기술적 사실관계를 "추정"으로 채우지 않는다. 모르면 `(작성 필요)`.

## 출력
- 변경 diff 요약 (어느 섹션이 이동/신설/수정되었는지)
- 남은 작성 필요 항목 리스트
