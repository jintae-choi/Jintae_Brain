## 개요
> **한 줄 요약: SPA는 브라우저가 JS로 화면을 만들고, RSC는 서버가 화면을 완성해서 준다(= 옛 PHP 방식). React가 SPA로 갔다가 다시 "서버가 만들어 주는" 방식으로 돌아온 흐름이다.**
>
> Next.js(App Router)를 쓰면 컴포넌트마다 "서버 컴포넌트냐 클라이언트 컴포넌트(`use client`)냐"를 정해야 한다. 이 선택의 본질은 딱 하나 — **이 화면을 누가·어디서 만드나**다. 이 노트는 SPA와 RSC를 "화면 만드는 주체"로 구분한다.

---

## 1. 큰 흐름 — 두 방식 대조

```
[SPA] (= 전부 use client, 2010년대 방식)
  브라우저 접속
    │ 서버는 "빈 껍데기 HTML + 큰 JS뭉치"만 전송
    ▼
  브라우저가 JS 실행 → 화면 그림
    │ 데이터 필요하면 /api 로 다시 요청 → 받아서 또 그림
    ▼
  ▶ 화면 만드는 주체 = 클라이언트(브라우저)

[RSC] (= React Server Component, 서버 렌더링의 귀환)
  브라우저 접속
    │ 서버가 DB 직접 읽어 "완성된 화면"을 전송
    ▼
  브라우저는 그냥 표시만
    │
    ▼
  ▶ 화면 만드는 주체 = 서버   ← 옛 PHP와 같은 철학
```

### 사전 지식 / 용어
- **SPA (Single Page Application)** — 첫 로드 때 JS 뭉치를 받아, 이후 화면 전환·갱신을 **브라우저가** JS로 처리하는 방식. 페이지 새로고침 없이 도는 웹앱.
- **RSC (React Server Component)** — 컴포넌트를 **서버에서** 실행해 완성된 UI를 내려보내는 React 방식. 서버 컴포넌트의 JS는 브라우저로 전송되지 않는다(번들이 가벼워짐).
- **`use client`** — 그 컴포넌트를 브라우저에서 도는 클라이언트 컴포넌트로 지정하는 선언. 버튼 클릭·입력·상태(useState) 같은 인터랙션은 여기서만 된다.
- **hydration** — 서버가 그려준 화면에 브라우저가 JS를 "덧입혀" 클릭 등이 먹게 만드는 과정.

## 2. 개념별 상세

### 2-1. SPA — 브라우저가 화면을 만든다

서버는 빈 껍데기 HTML과 JS 뭉치만 보낸다. 실제 화면 그리기는 브라우저가 JS를 실행해서 한다. 데이터가 더 필요하면 그때그때 `/api`로 추가 요청한다.

```
[브라우저]
   │ 1. index.html 받음 → 거의 빈 껍데기 (<div id="root"></div> + <script>)
   ▼
   2. 큰 JS 번들 다운로드 → 실행
   ▼
   3. JS가 화면(DOM)을 그림
   ▼
   4. 데이터 필요 → fetch('/api/...') → 받아서 다시 그림
```

- 장점: 첫 로드 후에는 화면 전환이 매끄럽다(서버 왕복 없이 JS가 바로 그림).
- 단점: 처음에 JS 뭉치가 커서 **초기 로딩이 느리고**, 검색엔진이 빈 껍데기를 볼 수 있으며(SEO 불리), 데이터를 항상 `/api`로 한 번 더 받아야 한다.

### 2-2. RSC — 서버가 화면을 완성해서 준다 (= PHP)

서버가 DB를 직접 읽어 **완성된 화면**을 만들어 보낸다. 브라우저는 받아서 보여주기만 하면 된다. 이것이 옛날 PHP가 하던 바로 그 방식이다.

```
[서버]
   │ 1. 요청 받음
   ▼
   2. 서버 컴포넌트 실행 → DB 직접 조회 (api 경유 안 함)
   ▼
   3. 완성된 UI를 만들어 전송
        [브라우저]
           ▼
        4. 받아서 표시 (이 컴포넌트의 JS는 안 받음 → 가벼움)
```

- 장점: 초기 화면이 빠르고(서버가 완성), DB를 서버에서 바로 읽어 `/api`가 불필요하며, 브라우저로 가는 JS가 줄어 가볍다. 대량의 표·목록 같은 **읽기 화면**에 특히 유리하다.
- PHP와 같은 철학: **"서버가 DB 읽고 HTML 만들어 던진다."** 그래서 RSC를 **"서버 렌더링의 귀환"**이라 부른다.

### 2-3. PHP와 뭐가 다른가 — 인터랙션 조각만 JS로

RSC가 PHP와 같은 철학이라면 왜 새로 나왔나? 차이는 **인터랙션 처리**다. 순수 PHP는 버튼 하나 눌러도 보통 페이지 전체를 다시 받는다. RSC는 서버가 완성해 주되, **클릭·입력이 필요한 조각만** `use client`로 지정해 그 부분에만 JS를 얹는다(이걸 "아일랜드"라 한다). 그래서 페이지 전체를 새로 받지 않고 그 조각만 반응해, PHP보다 매끄럽다.

```
서버가 완성한 페이지 (RSC)
   ├── 헤더·목록·표      ← 서버 컴포넌트 (JS 없음, 그냥 표시)
   └── [검색 입력창]      ← use client 아일랜드 (여기만 JS로 인터랙션)
```

## 3. 핵심 통찰

| 구분 | SPA (`use client` 전부) | RSC (서버 컴포넌트) |
|---|---|---|
| 화면 만드는 곳 | 브라우저 | 서버 |
| DB 접근 | 불가 → `/api` 경유 | 직접 가능 |
| 브라우저로 가는 JS | 큼(번들 전체) | 작음(서버 컴포넌트 제외) |
| 초기 로딩 | 느림 | 빠름 |
| 인터랙션(클릭·입력) | 어디서나 | 클라이언트 컴포넌트(아일랜드)만 |
| 옛 대응물 | — | **PHP 서버 렌더링** |

- ★ **"화면을 누가 만드나"가 전부다.** 서버 컴포넌트/클라이언트 컴포넌트의 모든 차이는 이 한 줄에서 갈린다.
- **RSC는 새 개념이 아니라 회귀다.** SPA가 브라우저로 렌더링을 다 옮겼다가, 초기 로딩·SEO 문제로 다시 서버로 되돌아온 것이다. PHP를 해봤다면 이미 아는 개념이다.
- **`use client`는 "예외" 표시다.** Next App Router의 기본은 서버 컴포넌트다. `use client`는 "이 조각은 브라우저가 맡아야 함(인터랙션 있음)"을 명시하는 선언이다.

## 4. 어느 걸 언제 — 고르는 기준

```
이 화면이 "읽어서 보여주기만" 하나? ──Yes──▶ 서버 컴포넌트 (RSC)
        └No, 입력·클릭·실시간 상태가 있나? ──Yes──▶ 그 조각(잎)만 use client
```

- **읽기 위주(대량 표·목록·상세 표출)** → RSC. 서버가 DB에서 바로 뽑아 완성하니 빠르고 가볍다.
- **편집·입력 위주(폼·필터·실시간)** → 그 부분만 클라이언트 컴포넌트.
- 근본 원칙: **서버 컴포넌트를 기본으로, 클라이언트는 인터랙션이 필요한 잎(leaf)에만.** "전부 `use client`"는 App Router를 SPA처럼 쓰는 것이라 서버 렌더링의 이점을 통째로 버리는 셈이다.

---

## 5. 한 줄 교훈

> **SPA는 브라우저가, RSC는 서버가 화면을 만든다. RSC = 옛 PHP처럼 "서버가 DB 읽어 완성해 주는" 방식의 귀환이다. 기본은 서버 컴포넌트, 인터랙션이 필요한 조각만 `use client`로 얹는다.**
