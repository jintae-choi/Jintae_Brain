# 개요
> Docker Compose는 여러 컨테이너의 설정을 **YAML 파일 하나**로 선언해 한 번에 실행하는 도구다. `docker run`을 길게 치는 대신 `docker compose up` 한 줄. 명령어는 [[1. Docker 명령어 치트시트]].

---

## 1. 전체 개념 / 흐름

### 1-1. 큰 그림 — 한 파일로 여러 서비스

```
[docker-compose.yml]  ──docker compose up -d──►  web + db + redis 동시 기동
   서비스 여러 개 선언                              (서비스 수만큼 컨테이너)
        │
        └─ 같은 compose = 자동으로 한 네트워크 → 서비스명으로 서로 접속
```

정의된 **서비스 수만큼 컨테이너가 동시에 실행**된다. compose 파일은 보통 **프로젝트(웹앱) 단위**로 하나 둔다.

### 1-2. 사전 지식 / 용어

- **호스트(host)** — 도커를 실행하는 **그 컴퓨터**(내 로컬 PC). 이미지·컨테이너·볼륨이 실제로 올라가 있는 바탕. Windows는 도커가 이 호스트 위의 WSL2 리눅스 안에서 돈다. 포트 매핑 `8080:80`의 `8080`도, bind mount `./src`의 `./src`도 모두 이 호스트 기준.
- **서비스(service)** — compose가 관리하는 컨테이너 한 종류(`web`, `db` …).
- **이미지 vs 빌드** — `image:`는 레지스트리 이미지를 받아 쓰고, `build:`는 로컬 Dockerfile로 굽는다.
- **`image:`(compose) vs `FROM`(Dockerfile)** — 둘 다 레지스트리에서 베이스 이미지를 가져오지만 역할이 다르다. `image: mysql:8.0`은 그 이미지를 **그대로 실행**(안 굽는다). `FROM php:8.1-apache`는 그 위에 내 걸 더 쌓아 **새 이미지를 굽는 시작점**. 즉 `image:`=완제품 실행, `FROM`=재료.
- **볼륨(volume)** — 데이터를 컨테이너 밖에 보관(아래 1-4에서 2종 구분).

### 1-3. 비교 — docker run vs compose, 그리고 v1 vs v2

**① `docker run` vs `docker compose`**

| 항목 | `docker run` | `docker compose` |
|---|---|---|
| 대상 | 컨테이너 1개 | 여러 개 묶음 |
| 설정 | 명령어로 직접 입력 | YAML로 선언 |
| 재현성 | 낮음 | 매우 높음 |
| 실무 | 거의 안 씀 | 표준 |

**② `docker-compose`(v1) vs `docker compose`(v2) — 최신 주의**

| 구분 | v1 (옛날) | v2 (2026 표준) |
|---|---|---|
| 명령어 | `docker-compose`(하이픈) | `docker compose`(**스페이스**) |
| 정체 | 파이썬 별도 바이너리 | Docker CLI 내장 플러그인(Go) |
| 상태 | **2025-04 완전 제거** | 유일한 정답 |

### 1-4. 볼륨 2종 — bind mount vs named volume

가장 헷갈리는 지점. `down -v`가 무엇을 지우는지가 여기서 갈린다.

| 종류 | 예시 | 실체 | `down -v`로 삭제? | 용도 |
|---|---|---|---|---|
| **bind mount** | `./src:/var/www/html` | **내 로컬 폴더** | 안 지움(안전) | 코드 실시간 반영(개발) |
| **named volume** | `db_data:/var/lib/mysql` | 도커가 관리하는 내부 저장소 | 지움 | DB 등 데이터 영속화 |

```
docker compose down -v
   ├─ bind mount (./src …)   → 그대로. 내 폴더라 도커가 못 건드림
   └─ named volume (db_data) → 삭제 (DB 초기화)
```

- **bind mount** — "내 로컬 폴더를 컨테이너에 비춰줘." 소유자가 나라서 도커가 못 지운다. 로컬 수정 → 컨테이너 즉시 반영.
- **named volume** — "도커야, 저장공간 만들어 데이터 담아둬." 도커가 **호스트(=도커를 실행하는 그 컴퓨터, 내 로컬 PC) 안의 전용 구역**에 만들어 관리한다(Windows는 도커가 도는 WSL2 가상 디스크 안). bind mount와 결정적 차이: bind는 내가 지정한 내 폴더라 탐색기로 열리지만, named volume은 **도커가 알아서 만든 구역이라 내가 탐색기로 직접 여는 위치가 아니다.** 소유·관리 주체가 도커라 `-v`로 지워지고, 컨테이너와 독립이라 컨테이너를 지웠다 다시 만들어도 데이터가 유지된다.

> 볼륨을 아예 안 붙이면 컨테이너 삭제 시 내부 파일이 사라진다. 그래서 **DB 데이터는 named volume**에 담는 게 표준.

**표준인 이유 — `down`은 볼륨을 안 지운다.** 흔한 오해: "컨테이너 내리면 DB도 사라지지 않나?" 아니다.

```
docker compose down       → 컨테이너만 삭제, named volume 남음
docker compose down -v     → 그때만 볼륨까지 삭제
```

그래서 컨테이너를 내렸다(`down`) 다시 올려도(`up`) **DB 데이터가 그대로 남는다.** named volume은 컨테이너와 독립된 도커 관리 저장소라, 컨테이너를 지워도 볼륨은 존재한다. 실서비스에선 이 named volume에 데이터를 두거나(소규모), 관리형 DB(예: AWS RDS)를 컨테이너 밖에 따로 둔다(대규모) — 어느 쪽이든 "데이터는 컨테이너 밖" 원칙은 같다.

## 2. 전체 예시 코드

```yaml title="docker-compose.yml"
services:
  web:
    build: .                      # 로컬 Dockerfile로 굽기
    ports:
      - "8080:80"                 # 호스트 8080 → 컨테이너 80
    volumes:
      - ./src:/var/www/html       # bind mount: 코드 실시간 반영
    depends_on:
      - db

  db:
    image: mysql:8.0              # 레지스트리 이미지 사용
    environment:
      MYSQL_ROOT_PASSWORD: root
    volumes:
      - db_data:/var/lib/mysql    # named volume: 데이터 영속

  redis:
    image: redis:7

volumes:
  db_data:                        # named volume 선언
```

```bash
docker compose up -d       # 3개 서비스 동시 기동
```

## 3. 라인별 해설

### 3-1. 서비스 정의

- `web.build: .` — 현재 폴더 Dockerfile로 이미지를 굽는다. `image:`와 달리 내 코드로 만든다.
- `ports: "8080:80"` — `"호스트:컨테이너"`. 브라우저는 `localhost:8080`, 컨테이너 내부 Apache는 80.
- `volumes: ./src:/var/www/html` — bind mount. 로컬 `./src` 수정이 즉시 반영.
- `depends_on: db` — `db`를 **먼저 기동**. 단, "포트 열림"까지 기다리진 않는다(순서만 보장).

### 3-2. 서비스 간 통신 — 네트워크

같은 compose의 서비스들은 **자동으로 한 네트워크에 묶인다.** 그래서 `web`은 DB 주소로 IP가 아니라 **서비스명 `db`**를 쓴다.

```php
// web 컨테이너 안의 코드
$host = "db";     // ← 서비스명이 곧 호스트명. "localhost" 아님
$port = 3306;
```

> 이게 멀티 컨테이너의 핵심. `web`에서 `localhost`로 DB를 찾으면 실패한다 — DB는 별도 컨테이너라 `db`라는 이름으로 접속해야 한다.

### 3-3. environment / volumes

- `environment` — 컨테이너에 주입할 환경변수. **값을 직접 나열**한다(`MYSQL_ROOT_PASSWORD: root`). `.env` **파일명을 값처럼 여기 주지 않는다.** 파일로 주려면 별도 키 `env_file: .env`(파일 안 값을 통째 주입)를 쓰거나, `environment`에 `${DB_PW}`처럼 `${}`로 치환한다. 이때 `.env`는 YAML이 아니라 **`KEY=VALUE` 형식**이다(`MYSQL_ROOT_PASSWORD=root` — 콜론이 아니라 **등호**). compose는 같은 폴더 `.env`를 자동으로 읽어 `${}`에 채운다. 비밀값 분리가 표준.
- `volumes:` (최상위) — named volume `db_data`를 선언. 서비스의 `db_data:/var/lib/mysql`이 이걸 참조.

## 4. 최신 포인트

### 4-1. `version:` 필드는 이제 쓰지 않는다

옛 compose 파일 맨 위의 `version: "3.9"`는 **불필요·무시된다.** 넣으면 `the attribute version is obsolete` 경고만 뜬다. **그냥 지운다.** (compose는 항상 최신 명세로 검증)

```yaml
# 옛날 (쓰지 않음)
version: "3.9"
services: ...

# 지금 — version 줄 삭제
services: ...
```

### 4-2. `docker compose watch` — 볼륨 없이 라이브 리로드

파일 변경을 감지해 컨테이너에 즉시 동기화(재빌드 없이). 2025년 정식화. bind mount의 대안으로, 무엇을 어떻게 동기화할지 세밀히 지정할 수 있다.

### 4-3. `up -d --build` 판단

- `docker compose up -d` — 기존 이미지로 기동.
- `docker compose up -d --build` — **Dockerfile·소스가 바뀌었을 때** 이미지부터 다시 굽고 기동.
- restart/up/build 구분표는 [[1. Docker 명령어 치트시트]] 참조.

## 5. 운영으로 옮길 때 바뀌는 것

로컬 compose를 그대로 운영에 쓰지 않는다. 보통 아래가 달라진다.

| 항목 | 로컬 | 운영 |
|---|---|---|
| 포트 | `8080:80` | `80:80` |
| 도메인 | `localhost` | 실제 도메인 |
| 볼륨 | 로컬 폴더(bind) | 서버 디스크·named volume |
| 환경변수 | 하드코딩·개발용 | `.env`로 분리 |
| HTTPS | 없음 | 인증서 추가 |

---

## 6. 교훈
- **compose 파일에서 `version:`은 뺀다.** 넣으면 경고, 안 넣어야 최신.
- **서비스끼리는 서비스명으로 접속한다.** `localhost`가 아니라 `db`.
- **데이터는 named volume, 코드는 bind mount.** `down -v`는 named volume만 지운다 — 로컬 폴더는 안전.
- **웹/DB/캐시를 컨테이너로 분리**하는 게 실무 표준. 서비스 수만큼 컨테이너.
