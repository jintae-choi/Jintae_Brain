## 개요
> 여러 단계 빌드(multi-stage build)는 한 Dockerfile 안에 작업대(단계)를 여러 개 두고, 마지막 실행용 단계에 **결과물만** 옮겨 담는 방식이다. 빌드 도구·소스 원본은 버리고 **운영 의존성 + 컴파일 결과**만 남긴다 → 이미지가 작아지고 서버에 소스가 남지 않는다. Dockerfile 기초는 [[3. Dockerfile]].

---

## 1. 전체 개념 / 흐름

### 1-1. 큰 그림 — 작업대 5개, 최종 이미지는 마지막 1개

```
base       ─ 공통 바닥: Debian + Node, 시간대, 작업 폴더 /app
 ├→ deps      ─ 의존성 전부 설치(빌드 도구 포함)        예: 약 660개
 │   └→ build    ─ 소스 복사 → 컴파일 → dist/ 생성
 ├→ prod-deps ─ 운영 의존성만 설치(npm ci --omit=dev)    예: 약 390개
 └→ runtime   ─ 깨끗한 base 위에
                 [prod-deps 의 node_modules] + [build 의 dist] + 정적 파일만 복사(COPY --from)
                 → 최종 이미지(서버에서 실행)
```

- deps·build 단계는 **최종 이미지에 들어가지 않는다.** runtime 이 필요한 결과물만 집어 온다.
- deps 를 따로 둔 이유 = 레이어 캐시. 패키지 목록 파일만 먼저 복사해 설치하는 원리는 [[3. Dockerfile]] 4장.

### 1-2. 사전 지식 / 용어

- **단계(stage)** — Dockerfile 의 `FROM … AS 이름` 한 덩어리. 조립 공정의 작업대 하나다.
- **target** — 몇 번째 작업대까지 만들지 지정하는 값(`--target runtime`). 그 작업대의 결과가 최종 이미지가 된다.
- **의존성(dependency, 줄여서 deps)** — 코드가 가져다 쓰는 외부 라이브러리. 목록은 `package.json`, 설치 결과는 `node_modules` 폴더다.
- **`npm ci`** — `package-lock.json`(잠금 파일)에 적힌 버전 그대로 정확히 설치하는 명령. `npm install` 과 달리 버전을 바꾸지 않는다.
- **빌드 시점 vs 실행 시점** — `RUN`·`COPY` 는 빌드 때 실행돼 결과가 이미지에 굳고, `ENV`·`USER`·`EXPOSE`·`CMD` 는 실행하지 않고 "켜질 때 이렇게 해라"는 설정만 적어 둔다. 포트·볼륨·비밀값처럼 **어디서 어떻게 켤지**는 Dockerfile 이 아니라 compose(또는 `docker run` 옵션)가 정한다 — [[4. Docker Compose]]. (`RUN`=빌드 1회, `CMD`=켤 때마다는 [[5. 컨테이너 생명주기]])

### 1-3. 비교 — 전체 의존성 vs 운영 의존성

`package.json` 의 라이브러리 목록은 두 칸으로 나뉜다.

```
package.json
├─ dependencies      ← 운영 의존성: 서버가 도는 동안 실제로 불러 쓰는 것
│    express(웹 서버) · pg(DB 접속) · exceljs(엑셀) · react …
└─ devDependencies   ← 개발 의존성: 만들고 고칠 때만 쓰는 도구
     typescript(컴파일러) · vite(화면 묶기 + 개발 서버) · sass · eslint · prettier · tsx
```

| 항목 | 전체 의존성 | 운영 의존성 |
|---|---|---|
| 설치 범위 | `dependencies` + `devDependencies` | `dependencies` 만 |
| 설치 명령 | `npm ci` | `npm ci --omit=dev` |
| 쓰는 단계 | deps → build(컴파일할 때) | prod-deps → runtime(실행할 때) |
| 개수 예 | 약 660개 | 약 390개 |

> 비유: 가구 공장의 「공구 + 부품」 vs 「완성 가구에 박힌 부품」. 조립이 끝나면 공구(typescript·vite)는 집에 안 들이고, 가구(dist)와 거기 박힌 부품(express·pg)만 들인다.

같은 원리로 **한 단계 빌드 vs 여러 단계 빌드**를 대조하면:

| 항목 | 한 단계 빌드(`FROM` 1개) | 여러 단계 빌드 |
|---|---|---|
| 최종 이미지 내용 | 빌드 도구 + 소스 원본 + 결과물 전부 | 운영 의존성 + 결과물만 |
| 이미지 크기 | 큼 | 작음 |
| 서버에 소스 코드 | 남음 | 안 남음 |

### 1-4. 구성요소 역할 — 단계별

| 단계 | 시작점 | 하는 일 | 결과물 | 최종 이미지에 남나 |
|---|---|---|---|---|
| base | Node 바닥 이미지 | 시간대·작업 폴더 등 공통 설정 | 공통 바닥 | 바닥으로 남음 |
| deps | base | 의존성 전부 설치 | `node_modules`(전체) | 안 남음 |
| build | deps | 소스 복사 → 컴파일 | `dist/` | `dist/` 만 복사돼 남음 |
| prod-deps | **base**(deps 아님) | 운영 의존성만 설치 | `node_modules`(운영용) | 복사돼 남음 |
| runtime | **base**(깨끗한 바닥) | 위 결과물만 골라 담기, 실행 설정 | 최종 이미지 | 이것이 최종 이미지 |

- prod-deps·runtime 이 deps 가 아니라 base 에서 다시 시작하는 점이 핵심이다. deps 를 이어받으면 개발 도구가 따라온다.

## 2. 전체 예시 코드

```dockerfile title="Dockerfile.runtime"
FROM node:22-slim AS base
ENV TZ=Asia/Seoul
WORKDIR /app

FROM base AS deps
COPY package.json package-lock.json ./
RUN npm ci

FROM deps AS build
COPY tsconfig.json vite.config.ts index.html ./
COPY src ./src
COPY public ./public
RUN npm run build

FROM base AS prod-deps
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

FROM base AS runtime
ENV NODE_ENV=production
COPY --from=prod-deps /app/node_modules ./node_modules
COPY package.json ./
COPY public ./public
COPY --from=build /app/dist ./dist
RUN mkdir -p /app/logs && chown node:node /app/logs
USER node
EXPOSE 3000
CMD ["node", "dist/server/index.js"]
```

```text title="Dockerfile.runtime.dockerignore"
*
!package.json
!package-lock.json
!tsconfig.json
!vite.config.ts
!index.html
!src
!public
```

```bash
docker build -f Dockerfile.runtime --target runtime -t my-app .
```

## 3. 라인별 해설

### 3-1. 빌드 명령

- `-f Dockerfile.runtime` — 설계도 파일 지정. 기본 이름 `Dockerfile` 이 아닐 때 쓴다(개발용 `Dockerfile` 과 구분).
- `--target runtime` — runtime 단계까지 만들고 그 결과를 최종 이미지로 한다.
- `-t my-app` — 만든 이미지에 `my-app` 이름표(tag)를 붙인다.
- `.` — 빌드 컨텍스트(도커에 보내는 재료 창고). 이때 `.dockerignore` 로 걸러진 파일만 간다.
- `Dockerfile.runtime.dockerignore` — `<Dockerfile 이름>.dockerignore` 파일이 있으면 그 Dockerfile 로 빌드할 때만 이 제외 목록이 쓰인다(BuildKit 기능). 개발용 `Dockerfile` 은 기존 `.dockerignore` 를 그대로 쓴다.
- `*` 후 `!파일` — 일단 전부 빼고 `!` 붙은 것만 다시 넣는 **허용 목록** 방식. `.env`(비밀값)·큰 폴더·`node_modules` 가 실수로 넘어가는 일을 막기 쉽다.

### 3-2. 단계 연결

- `FROM base AS deps` — base 를 이어받아 `deps` 라는 새 작업대를 연다. `AS 이름` 이 단계 이름이다.
- `FROM deps AS build` — 의존성이 깔린 deps 를 이어받아 컴파일한다. 컴파일러(typescript)가 여기 필요하다.
- `npm run build` — `package.json` 의 build 스크립트 실행. 이 예에선 서버 TypeScript → JavaScript, 화면 코드는 vite 로 묶어 `dist/` 에 낸다.
- `FROM base AS prod-deps` — deps 가 아니라 깨끗한 base 에서 다시 시작한다.
- `--omit=dev` — `npm ci` 에서 `devDependencies` 를 빼고 설치한다.
- `COPY --from=prod-deps /app/node_modules ./node_modules` — `--from=단계` 로 다른 작업대의 결과물을 가져온다. 여러 단계 빌드의 연결 고리다.
- `COPY --from=build /app/dist ./dist` — 컴파일 결과만 가져온다. `src/`(소스 원본)는 가져오지 않는다.
- `ENV NODE_ENV=production` — 서버가 운영 모드로 뜨게 하는 환경변수 기본값.
- `chown node:node /app/logs` — 쓰기 폴더의 주인을 `node` 사용자로 바꾼다. 아래 `USER node` 로 root 가 아닌 사용자로 실행하므로 미리 쓰기 권한을 준다.
- `USER node` — 이후 일반 사용자 `node` 로 실행한다. 앱이 뚫려도 컨테이너 안에서 할 수 있는 일이 줄어든다.
- `EXPOSE 3000` — "이 이미지는 3000 포트를 쓴다"는 안내 표시. 실제 포트 연결은 compose 의 `ports` 가 한다.

### 3-3. 따라가 보기 — 파일 하나가 실행되기까지

```
src/server/index.ts (TypeScript 원본)
 → build 단계: typescript(개발 의존성)가 컴파일 → dist/server/index.js
 → runtime: node 가 index.js 실행 → require('express')
 → express 는 운영 의존성이라 runtime 에 있음 → 정상
   typescript 는 runtime 에 없음 → 이미 컴파일이 끝나 필요 없음
```

## 4. 핵심 통찰
- **빌드에 필요한 것 ≠ 실행에 필요한 것.** 여러 단계 빌드는 이 둘을 작업대로 갈라, 실행에 필요한 것만 최종 이미지로 보낸다.

## 5. 경험과 교훈 / 트러블슈팅

### 함정: 운영 이미지를 `NODE_ENV=development` 로 띄우면 시작 실패

**원인**: 개발 모드의 서버는 개발 서버(vite)를 불러오려 한다. vite 는 개발 의존성이라 `--omit=dev` 로 만든 운영 이미지에 없다.

**해결**: 운영 이미지는 `NODE_ENV=production` 으로 띄운다. 개발 모드가 필요하면 전체 의존성이 든 개발용 단계·이미지를 쓴다.

## 6. Best Practices — 운영 이미지 관행

- **가벼운 바닥 이미지**(`-slim`)를 쓴다.
- **한 Dockerfile 에 개발용 단계(`dev`)와 운영용 단계(`runtime`)를 같이 두고 `--target` 으로 골라 만드는** 방식도 흔하다.
- **프로세스 관리자(PM2) 없이 `node` 를 직접 실행**하고, 죽으면 재시작은 도커(compose `restart: unless-stopped`)가 맡긴다. 컨테이너 안에서 PM2 를 쓴다면 `pm2-runtime` — [[5. 컨테이너 생명주기]].
- **`USER node`** — root 가 아닌 일반 사용자로 실행한다. 쓰기 폴더는 그 전에 `chown` 으로 권한을 준다.
- **비밀값(`.env`·키 파일)은 이미지에 굽지 않는다.** 실행할 때 env_file·볼륨으로 넣는다 — [[4. Docker Compose]].
- **상태 확인(healthcheck)** 은 이미지에 curl 을 넣는 대신 `node -e "fetch(…)"` 로 한다(이미지에 도구를 늘리지 않음).
- **`.dockerignore` 는 허용 목록**(`*` + `!필요한것`)으로 쓴다.
