## 개요
> Quartz 마크다운이 GitHub Pages 공개 URL까지 도달하는 전체 파이프라인이다. `git push` 한 번에 GitHub Actions 임시 VM이 빌드를 수행하고, 결과 HTML이 GitHub 웹서버에 올라가 전 세계에서 접속 가능해진다.

---

## 1. 전체 개념 / 흐름

### 1-1. 파이프라인 한눈에

```
[내 PC] ──push main──► [GitHub 저장소]
                           │
                           ▼  (on.push.branches 트리거)
                     [GitHub Actions VM 생성]
                           │
                           │  npm ci
                           │  npx quartz build
                           │  → public/ 폴더(HTML) 생성
                           ▼
                     [GitHub Pages 스토리지에 public/ 업로드]
                           │
                           ▼  (VM 폐기)
                     [GitHub 웹서버가 HTML 호스팅]
                           │
                           ▼
                     https://jintae-choi.github.io/Jintae_Brain/
```

### 1-2. 사전 지식 / 용어

본문 이해에 필요한 배경 지식이다.

**정적 사이트 vs 동적 사이트**

| 항목 | 정적 사이트 | 동적 사이트 |
|---|---|---|
| 구성 | HTML/CSS/JS 파일만 | 서버측 언어 + DB |
| 요청 처리 | 서버가 파일 그대로 반환 | 서버가 매 요청마다 계산해서 HTML 생성 |
| 예시 | Quartz, Jekyll, Hugo | Node.js·PHP·Django 앱 |
| GitHub Pages 지원 | ✅ | ❌ |

Quartz는 마크다운을 **빌드 시점에** HTML로 미리 변환하므로 정적 사이트다. GitHub Pages는 정적 파일만 호스팅 가능하다.

**CI/CD와 이벤트 훅**

CI/CD는 Continuous Integration / Continuous Deployment의 약자이다. 코드가 바뀔 때마다 자동으로 빌드·테스트·배포를 수행하는 자동화 체계를 가리킨다. Jenkins가 같은 카테고리의 대표 도구다.

이벤트 훅은 특정 이벤트가 일어나면 미리 정해둔 작업이 자동 실행되는 장치이다. `deploy.yml`의 `on.push.branches`는 "main 브랜치에 push되면"이라는 훅이다. 이 프로젝트의 `.claude/hooks/` 디렉토리에 있는 Git hooks는 로컬 훅이고, Actions는 GitHub 서버 훅이다. 계층만 다를 뿐 철학은 동일하다.

**GitHub Actions**

GitHub Actions는 GitHub이 리포지토리에 내장해 제공하는 **CI/CD 플랫폼**이다. 이벤트(push·PR·릴리즈·수동 실행 등)가 발생하면 `.github/workflows/` 안의 YAML 스크립트를 GitHub 서버에서 자동 실행한다. 빌드 실행 환경은 GitHub이 즉석에서 생성하는 임시 VM이며, 작업이 끝나면 VM을 폐기한다. 공식 액션(예: `actions/checkout`·`actions/setup-node`)을 조합해 스크립트를 짠다. 이 프로젝트는 `.github/workflows/deploy.yml` 하나로 Quartz 빌드와 GitHub Pages 배포를 자동화한다.

**OIDC (OpenID Connect)**

OIDC는 비밀번호 없이 신원을 증명하는 방식이다. 비유하자면 **놀이공원 손목밴드**다.

- 옛날 방식: 배포하려면 GitHub Secrets에 AWS/Azure 비밀번호를 저장해야 했다. 유출 위험이 상존했다.
- OIDC 방식: GitHub이 "이 워크플로우는 진짜 이 리포의 main 브랜치에서 실행 중"임을 증명하는 **서명된 임시 토큰**을 즉석 발급한다. 상대 서비스(GitHub Pages 등)가 그 토큰을 보고 임시 권한을 부여한다. 작업이 끝나면 토큰은 자동 만료된다.

### 1-3. 로컬 개발 vs 원격 배포

이미 익숙한 `docker-compose.yml`과 대비해 `deploy.yml`의 성격을 파악한다.

| 항목 | `docker-compose.yml` | `deploy.yml` |
|---|---|---|
| 실행 장소 | 내 PC | GitHub 서버 |
| 실행 주체 | Docker 엔진 | GitHub Actions |
| 트리거 | 내가 `up` 명령 칠 때 | `main`에 push될 때 자동 |
| 환경 | 컨테이너 | 가상머신(VM) |
| 수명 | 내가 `down`할 때까지 유지 | 빌드 끝나면 자동 삭제 |
| 목적 | 개발 중 미리보기 | 실제 사이트 배포 |

두 파일 모두 "격리된 환경에서 정해진 명령어를 순서대로 돌린다"는 본질은 같다. 차이는 **장소와 수명**이다.

### 1-4. 구성요소 역할

파이프라인 각 단계의 구성요소와 수명을 정리한다.

| 구성요소 | 역할 | 수명 |
|---|---|---|
| 내 PC | 마크다운 작성·커밋·push | 상시 |
| `deploy.yml` | GitHub Actions에게 "이렇게 빌드해라" 지시하는 스크립트 | 리포 수명 |
| GitHub Actions VM | 빌드 실행 전용 임시 우분투 가상머신 | push 1회당 수 분 |
| `public/` 폴더 | Quartz 빌드 결과물 (정적 HTML·CSS·JS) | VM 종료와 함께 사라지지만 Pages 스토리지로 복사됨 |
| GitHub Pages 스토리지 | HTML 파일 영구 보관소 | 다음 배포 시 덮어쓰기 |
| GitHub 웹서버 | 공개 URL로 HTML 서빙 | 상시 |

## 2. 전체 예시 코드

프로젝트 `.github/workflows/deploy.yml` 전문이다.

```yaml title=".github/workflows/deploy.yml"
name: Deploy Quartz site to GitHub Pages

on:
  push:
    branches:
      - main
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: "pages"
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - name: Install Dependencies
        run: npm ci

      - name: Build Quartz
        run: npx quartz build

      - name: Setup Pages
        uses: actions/configure-pages@v5

      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: public

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

## 3. 라인별 / 포인트별 상세 해설

### 3-1. 트리거 (`on`)

```yaml
on:
  push:
    branches:
      - main
  workflow_dispatch:
```

- `on` — 워크플로우를 언제 실행할지 정의하는 최상위 키이다.
- `push.branches: [main]` — `main` 브랜치에 push가 들어올 때만 실행한다. 다른 브랜치 push는 무시된다.
- `workflow_dispatch` — GitHub 웹 UI의 "Run workflow" 버튼으로 수동 실행할 수 있게 허용한다.

> **용어박스: 워크플로우(workflow)**  
> GitHub Actions의 실행 단위이다. `.github/workflows/*.yml` 파일 하나가 하나의 워크플로우이며, 여러 개의 Job을 순차·병렬로 엮을 수 있다.

### 3-2. 권한 (`permissions`)

```yaml
permissions:
  contents: read
  pages: write
  id-token: write
```

- `contents: read` — 리포지토리 코드를 읽을 권한이다. 체크아웃에 필요하다.
- `pages: write` — GitHub Pages 배포용 쓰기 권한이다.
- `id-token: write` — OIDC 토큰 발급 권한이다. **비밀번호가 아니라 "증명서 받을 권한"**이므로 공개돼도 안전하다. 자세한 설명은 [1-2. 사전 지식 / 용어](#1-2-사전-지식--용어)의 OIDC 항목 참고.

### 3-3. 동시성 제어 (`concurrency`)

```yaml
concurrency:
  group: "pages"
  cancel-in-progress: false
```

- `group: "pages"` — 같은 그룹 이름을 가진 워크플로우는 동시에 하나만 실행된다. 여러 push가 겹쳐도 배포가 꼬이지 않는다.
- `cancel-in-progress: false` — 진행 중인 배포가 있으면 새 배포는 **취소하지 않고 대기**한다. `true`로 두면 새 push가 기존 배포를 중단시킨다.

### 3-4. Build Job

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
```

- `jobs.build` — 첫 번째 job의 이름이다. 이 job이 빌드를 담당한다.
- `runs-on: ubuntu-latest` — GitHub이 최신 우분투 VM을 하나 생성하라는 지시이다. Windows·macOS도 선택 가능하다.

```yaml
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
```

- `uses: actions/checkout@v4` — 리포지토리 코드를 VM에 복제하는 공식 액션이다.
- `fetch-depth: 0` — 전체 git 히스토리를 가져온다. Quartz가 "마지막 수정 날짜" 표시에 커밋 히스토리를 활용하므로 필요하다.

```yaml
      - uses: actions/setup-node@v4
        with:
          node-version: 22
```

- `actions/setup-node@v4` — VM에 Node.js를 설치하는 공식 액션이다.
- `node-version: 22` — Node.js 22버전을 설치한다.

```yaml
      - name: Install Dependencies
        run: npm ci
```

- `npm ci` — `package-lock.json` 기준으로 의존성을 정확히 재현 설치한다. `npm install`과 달리 lock 파일을 갱신하지 않는다. CI 환경에서는 `ci`가 표준이다.

```yaml
      - name: Build Quartz
        run: npx quartz build
```

- `npx quartz build` — Quartz 엔진이 `content/`의 마크다운을 읽어 `public/` 폴더에 정적 HTML·CSS·JS를 생성한다.

```yaml
      - name: Setup Pages
        uses: actions/configure-pages@v5

      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: public
```

- `configure-pages@v5` — GitHub Pages 설정을 워크플로우에 주입한다 (도메인·경로 등).
- `upload-pages-artifact@v3` — `public/` 폴더를 Pages 배포용 아티팩트로 업로드한다. 이 아티팩트는 다음 deploy job이 받아 쓴다.

### 3-5. Deploy Job

```yaml
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
```

- `needs: build` — build job이 성공해야만 deploy job이 시작된다는 의존 관계 선언이다.
- `environment.name: github-pages` — GitHub Pages 전용 환경에서 실행한다. 리포 설정의 Environment 보호 규칙이 적용된다.
- `url: ${{ ... page_url }}` — 배포 완료 시 GitHub UI에 표시할 사이트 URL이다.

```yaml
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

- `actions/deploy-pages@v4` — 앞서 업로드한 아티팩트를 실제 Pages 서버에 배포하는 공식 액션이다. 이 단계에서 OIDC 토큰이 사용된다.
- `id: deployment` — 이 스텝 출력값을 `steps.deployment.outputs.page_url`로 참조하기 위한 ID이다.

## 4. 경험과 교훈 / 트러블슈팅

### ❌ 실패: 사이트가 최신 내용이 아니었음

**증상**: https://jintae-choi.github.io/Jintae_Brain/ 에 접속했지만 **옛날 커밋 시점의 화면**이 그대로 표시되고, 테마 스위처·Docker dev 모드 학습 노트·Claude 자동화 자산 등 최근 작업이 반영되지 않았다.

**원인**: `deploy.yml`은 `main` 브랜치 push에만 트리거된다. 그런데 최근 작업은 모두 `feat/design-theme-switcher` 브랜치에만 쌓였고, `main`은 `21dcc11`(Claude 자동화 자산 추가 및 docs/ 구조 정리) 커밋에서 멈춰 있었다. 브랜치 분기 상태를 확인하지 않고 "push했으니 반영됐겠지"라고 가정한 것이 근본 원인이다.

```bash
# 증거 수집
$ git log --oneline main..feat/design-theme-switcher
a811a47 chore: Agentic AI 폴더에서 빈/중복 파일 정리
faf7066 chore: Claude 확장 포인트(hooks/commands/MCP) 정비
7c657e4 docs: Docker 개발 모드·디자인 테마 스위처 학습 노트로 이동/추가
471f0ac chore: Docker 개발 모드 분리 및 포트 8080 통일
f53b6df feat: 디자인 테마 스위처(A/B/C) 추가
```

- `--oneline` — 각 커밋을 해시 + 제목 한 줄로 요약 출력하는 플래그이다.
- `main..feat/design-theme-switcher` — `A..B` 형식은 "A에는 없고 B에만 있는 커밋"을 나열하는 git 범위 표기이다. 두 브랜치 차이 확인 전용.

5커밋이 `main`에 반영되지 않은 상태였다.

**해결**:
```bash
# feat 브랜치를 main에 머지한다 (PR 또는 fast-forward)
git checkout main
git merge feat/design-theme-switcher   # fast-forward (일직선 머지)
git push origin main
# → GitHub Actions가 자동 실행
# → 수 분 후 사이트 갱신 완료
```

**교훈**:
- "push했다"와 "배포됐다"는 다르다. **배포 트리거 브랜치**(여기선 `main`)에 도달해야 사이트가 갱신된다.
- feature 브랜치에서만 작업하면 아무리 push해도 사이트는 안 바뀐다.
- 장기 작업 중에는 주기적으로 `git log --oneline main..HEAD`로 main과의 격차를 확인한다.

## 5. Best Practices

### 5-1. 로컬 빌드 vs Actions 빌드

로컬에서 `npx quartz build` 후 `gh-pages` 브랜치에 `public/`을 푸시하는 방식도 기술적으로 가능하다. 그러나 Actions 방식이 표준이 된 이유는 다음과 같다.

| 비교 항목 | 로컬 빌드 push | Actions 빌드 (현재) |
|---|---|---|
| 빌드 누락 위험 | 마크다운만 push하면 사이트는 그대로 — 빌드 까먹기 쉬움 | 자동 — 실수 불가능 |
| 환경 일관성 | 내 PC Node 버전·캐시에 따라 결과 다름 | 매번 깨끗한 우분투 22·Node 22 → 결정적 |
| git 히스토리 | 기계 생성 HTML 수만 줄이 커밋에 섞임 → 노이즈 | 내가 짠 마크다운만 커밋 → 깔끔 |
| 여러 PC 작업 | Node·Quartz 세팅된 PC에서만 가능 | push만 하면 어디서든 배포 |

따라서 `.gitignore`에 `public/`을 넣어 빌드 결과물이 커밋되지 않게 한다.

### 5-2. 브랜치 머지 방식 선택

| 방식 | 언제 쓰나 | 특징 |
|---|---|---|
| fast-forward 머지 | 개인 프로젝트, 공부 레포, 일직선 히스토리 원할 때 | `main` 포인터를 단순 전진. 새 머지 커밋 없음. 깔끔 |
| Pull Request | 팀 작업, 변경 이력을 웹에 남기고 싶을 때 | 웹에서 diff·리뷰·이력 추적 가능. 머지 커밋 생성 |

혼자 쓰는 공부 레포라도 PR을 쓰면 GitHub 웹에서 "이 기능을 왜 추가했는지" 추적하기 쉽다.

### 5-3. main 배포 전 체크리스트

- [ ] 작업트리 clean (`git status`)
- [ ] feature 브랜치에서 main과의 diff 확인 (`git log main..HEAD`)
- [ ] 로컬 미리보기 확인 (`docker-compose up -d` → http://localhost:8080)
- [ ] 시크릿·개인정보 미포함 여부 확인
- [ ] 머지 후 Actions 실행 상태 확인 (GitHub 웹 → Actions 탭)
- [ ] 배포 URL 접속해서 실제 갱신 확인
