## 개요
> Node.js 앱을 백그라운드로 띄우고 크래시·재부팅에도 살아 있게 관리하는 프로세스 매니저 pm2의 명령어와 함정을 워크플로우 순서로 정리한 것이다. 명령어 나열이 아니라 "언제 무엇을 쓰나"에 초점을 둔다.

---

## 1. 큰 그림 / 왜 pm2인가

### 1-1. `node app.js`와 대조 — 무엇이 아쉬워서 pm2를 쓰나

`node app.js`로 직접 띄우면 개발 중엔 되지만 서버 운영엔 구멍이 많다. pm2는 그 구멍을 메운다.

| 항목 | `node app.js` (직접 실행) | pm2 |
|---|---|---|
| 실행 위치 | 포그라운드(터미널 점유) | 백그라운드 데몬 |
| 터미널을 닫으면 | 프로세스도 죽음 | 계속 실행 |
| 앱이 크래시하면 | 그대로 멈춤 | 자동 재시작 |
| 서버 재부팅 후 | 수동으로 다시 실행 | 자동 시작(startup+save) |
| 앱 여러 개 | 터미널 여러 개로 관리 | 한 목록에서 관리 |
| CPU 코어 | 1개만(싱글 스레드) | 클러스터 모드로 코어 수만큼 |
| 로그 | 직접 파일로 리다이렉트 | `pm2 logs`로 통합 |

> **한 줄 요약**: pm2 = "안 죽고, 알아서 되살아나고, 재부팅에도 살아나는" node 실행기.

### 1-2. 생명주기 흐름

명령어를 외우지 말고 흐름으로 기억한다.

```
[코드 / ecosystem.config.cjs]
        │
        ▼
pm2 start ecosystem.config.cjs ──► 앱 데몬으로 실행 ──► pm2 list (상태 확인)
                                         │
                    pm2 logs <앱> ──► 로그 확인
                    pm2 monit     ──► 실시간 CPU·메모리 대시보드
                                         │
   ┌─────────────────────────────────────┘
   ▼
코드만 바꿈   ──► pm2 reload  <앱>   (무중단 교체)
설정·env 바꿈 ──► pm2 restart <앱>   (껐다 켬)
잠깐 멈춤     ──► pm2 stop    <앱>   (목록엔 남음)
아예 내림     ──► pm2 delete  <앱>   (목록에서 제거)
   │
   ▼
재부팅에도 유지 ──► pm2 startup (부팅 등록) + pm2 save (현재 목록 저장)
```

### 1-3. 사전 지식 / 용어

- **데몬(daemon)** — 터미널과 분리돼 백그라운드에서 도는 상주 프로세스. pm2가 앱을 데몬으로 띄운다.
- **fork 모드 / cluster 모드** — fork = 프로세스 1개(기본). cluster = 같은 앱을 CPU 코어 수만큼 복제해 부하 분산 + 무중단 배포 가능.
- **무중단(0-downtime)** — 새 프로세스를 먼저 띄우고 나서 옛 프로세스를 내려, 요청이 한 번도 끊기지 않는 것.
- **ecosystem 파일** — 앱 이름·진입점·인스턴스 수·환경변수를 담은 pm2 설정 파일. 명령어 옵션을 매번 안 쳐도 되게 한다.

## 2. 명령어 표

### 2-1. 실행·조회 (매일)

| 명령어 | 뜻 | 풀네임/비고 |
|---|---|---|
| `pm2 start ecosystem.config.cjs` | 설정 파일로 앱 실행 | 운영 표준 |
| `pm2 start app.js --name my-api` | 단일 파일 실행 + 이름 지정 | 빠른 테스트용 |
| `pm2 list` (= `pm2 ls`) | 관리 중인 프로세스 목록·상태 | list |
| `pm2 logs [앱]` | 로그 실시간 출력 | 앱 생략 시 전체 |
| `pm2 monit` | 실시간 CPU·메모리 대시보드 | **monit**or |

### 2-2. 교체·중단 (배포할 때)

| 명령어 | 뜻 | 주의 |
|---|---|---|
| `pm2 reload <앱\|all>` | **무중단** 재시작 | cluster 모드라야 진짜 0-downtime |
| `pm2 restart <앱\|all>` | 껐다 켬(순단 발생) | 설정·env 바꿨을 때 |
| `pm2 stop <앱\|all>` | 멈춤(목록엔 `stopped`로 남음) | 되살리려면 restart |
| `pm2 delete <대상>` | 목록에서 제거 | = `pm2 del` |

`pm2 delete`의 세 가지 대상 지정:

```bash
pm2 delete all      # 전부 제거
pm2 delete 0        # id로 (pm2 list의 맨 앞 숫자)
pm2 delete my-api   # name으로 (ecosystem의 name)
```

### 2-3. 재부팅 생존 (서버 세팅 시 1회)

| 명령어 | 뜻 |
|---|---|
| `pm2 startup` | OS 부팅 시 pm2를 자동 시작하도록 등록(출력되는 명령을 한 번 실행) |
| `pm2 save` | 지금 목록을 저장 → 부팅 후 이 목록으로 복원 |

> `startup`만 하고 `save`를 안 하면 부팅돼도 복원할 목록이 없다. **둘은 세트**다.

### 2-4. Node 버전 확인·데몬 교체 (Node를 올린 뒤)

| 명령어 | 뜻 | 볼 곳 |
|---|---|---|
| `pm2 describe <앱>` | 앱 1개의 상세 정보 | `node.js version` 줄 = 그 앱이 지금 도는 Node 버전 |
| `pm2 report` | pm2 진단 보고서 | `Daemon` 칸의 `node version` = 데몬, `CLI` 칸의 `node version` = 방금 친 `pm2` 명령. 두 줄은 칸 제목과 `argv`로 구분한다 |
| `pm2 update` | 데몬을 새로 띄우고 앱 전체를 되살림 | 앱이 전부 한 번 내려갔다 뜬다 → 5-3 |

## 3. 핵심 함정 — reload vs restart

가장 자주 헷갈리는 지점. 이름은 비슷하지만 하는 일이 다르다.

| 구분 | `restart` | `reload` |
|---|---|---|
| 방식 | 프로세스를 죽이고 새로 띄움 | 새 프로세스를 띄운 뒤 옛 것을 내림 |
| 다운타임 | 있음(짧게 끊김) | 없음(0-downtime) |
| 진짜 무중단 조건 | — | **cluster 모드** 필요 |
| 환경변수 갱신 | `--update-env` 붙여야 반영 | `--update-env` 붙여야 반영 |
| 언제 쓰나 | 설정·환경변수 바꿨을 때 | 코드만 바꿔 무중단 배포할 때 |

> **함정 1 — fork 모드에서 reload는 무중단이 아니다.** pm2는 fork 모드 앱의 reload를 restart로 대신한다(옛 프로세스를 끄고 새로 켬 → 순간 끊김). cluster 모드면 pm2가 인스턴스마다 새 워커를 먼저 띄우고, 새 워커가 포트를 듣기 시작한 뒤 옛 워커를 내린다 — 그래서 `exec_mode: "cluster"`면 `instances: 1`이어도 reload가 무중단이다. `instances: 2` 이상은 무중단 조건이 아니라, 한 인스턴스가 죽어도 다른 인스턴스가 요청을 받는 이중화 이점이다.
>
> **함정 2 — 환경변수를 바꿨는데 반영이 안 된다.** reload·restart는 기본적으로 옛 env를 그대로 물려준다. `.env`나 ecosystem의 `env`를 고쳤으면 `pm2 restart my-api --update-env`.

## 4. ecosystem.config.cjs — 왜 `.cjs`인가

### 4-1. 확장자가 `.cjs`인 이유

```
package.json 에 "type": "module" (ESM 프로젝트)
        │
        ▼
.js 파일 = ESM으로 해석  ──► module.exports = {...} 쓰면 에러
        │
        ▼
확장자를 .cjs 로 → Node가 강제로 CommonJS로 읽음 → pm2 설정 문법 정상 동작
```

pm2 설정은 `module.exports =`(CommonJS) 문법이다. 프로젝트가 ESM(`"type": "module"`)이면 `.js`가 ESM으로 읽혀 충돌하므로, 확장자를 **`.cjs`로 고정**해 CommonJS로 강제한다. ESM 프로젝트가 아니면 `ecosystem.config.js`도 된다.

### 4-2. 전체 예시

```js
// ecosystem.config.cjs
module.exports = {
  apps: [
    {
      name: "my-api",              // pm2 list에 뜨는 이름
      script: "./dist/server.js",  // 실행할 진입점
      instances: "max",            // 클러스터: CPU 코어 수만큼 복제
      exec_mode: "cluster",        // fork(기본) 대신 cluster
      env: {                       // 기본 환경변수
        NODE_ENV: "production",
        PORT: 3000,
      },
    },
    // 앱을 더 넣으려면 이 배열에 객체를 추가
  ],
};
```

| 필드 | 뜻 |
|---|---|
| `name` | 프로세스 이름. reload/restart/delete에서 이 이름으로 지목 |
| `script` | 실행할 진입 파일 |
| `instances` | 몇 개 띄울지. `"max"` = 코어 수, 숫자 지정도 가능 |
| `exec_mode` | `fork`(1개) vs `cluster`(N개·무중단 가능) |
| `env` | 앱에 주입할 환경변수 |
| `interpreter` | 앱을 띄울 node 실행 파일(예시엔 없음, 기본값 `node`). fork 모드에서만 쓰인다 → 5-2 |

> 설정 파일의 이점: `pm2 start server.js --name my-api --instances max ...`를 매번 손으로 치지 않고, 파일 하나로 **똑같이 재현**한다. 그래서 `pm2 start ecosystem.config.cjs` 한 줄이 운영 표준이다.

## 5. Node 버전 — 프로세스마다 따로 정해진다

### 5-1. 버전이 정해지는 시점

- 실행 중인 Node 프로세스의 버전은 **그 프로세스가 켜질 때 디스크에 있던 node 실행 파일의 버전**이다.
- 프로세스는 켜지면서 실행 파일을 메모리에 올린다. 그래서 나중에 디스크의 파일을 새 버전으로 바꿔도 이미 돌고 있는 프로세스는 옛 버전 그대로다.
- 새 버전이 적용되는 때 = 그 프로세스를 **다시 띄울 때**뿐이다.

### 5-2. 데몬과 앱은 버전이 따로다

pm2 데몬(→ 1-3 용어)도 Node 프로그램이라 자기 Node 버전이 있다. 앱은 데몬이 띄운 자식 프로세스라, 각자 켜진 시점의 버전으로 돈다. 같은 경로의 node 실행 파일을 22.14.0 → 22.23.4로 덮어쓴 예:

```
[교체 전] node 실행 파일 = 22.14.0
   ├─ pm2 데몬 시작 → 데몬 = 22.14.0 (계속 그대로)
   └─ my-api·my-worker 시작 → 두 앱 = 22.14.0

[교체] 같은 경로의 node 실행 파일을 22.23.4로 덮어씀

[교체 후] 배포 → pm2 reload my-api
   ├─ 데몬이 my-api를 다시 띄움 → my-api = 22.23.4 (실행 파일을 다시 읽음)
   └─ my-worker는 안 건드림 → my-worker = 22.14.0 그대로
```

> **비유**: 데몬은 관리자, 앱은 관리자가 배치한 직원이다. 관리자가 옛 사람이어도 새로 뽑은 직원은 새 사람이다.

앱을 어느 node 실행 파일로 띄우는지는 실행 모드(→ 1-3 fork/cluster)에 따라 다르다(pm2 7.1.1 소스 기준):

| 실행 모드 | 앱을 띄우는 node | `interpreter` 설정 |
|---|---|---|
| fork | `interpreter` 값(기본 `node`) | 쓰인다 — 다른 node 경로를 주면 아예 다른 Node 버전으로 뜬다 |
| cluster | 데몬 자신의 node 실행 파일 경로 | 쓰이지 않는다 |

- 위 예처럼 **같은 경로에 덮어쓰면** 두 모드 모두 다시 띄운 앱이 새 버전이 된다.
- 새 버전을 **다른 경로에 설치하면**(버전 관리 도구 nvm 등) cluster 모드 앱은 데몬이 쓰는 옛 경로로 계속 뜬다 → 데몬까지 올려야 한다(5-3).

### 5-3. Node를 올린 뒤 적용하는 법

| 대상 | 방법 | 영향 |
|---|---|---|
| 앱 | `pm2 reload <앱>` 또는 `pm2 restart <앱>`으로 다시 띄움 | fork 모드면 순간 끊김(→ 3장 함정 1) |
| 앱 (배포 때 이미 reload 하는 구조) | 할 일 없음 — 다음 배포 때 자연히 적용 | 없음 |
| 데몬 | `pm2 update` | 앱 전체가 한 번 내려갔다 뜬다 |

`pm2 update`가 하는 일(pm2 소스 `lib/API.js`의 `update`):

```
pm2 update
   │
   ├─ 1. 지금 목록을 저장 (pm2 save 와 같은 저장 — 기존 저장본을 덮어씀)
   ├─ 2. 데몬 종료 (앱 전체도 함께 내려감)
   ├─ 3. 데몬 새로 시작 (pm2 update 를 친 그 pm2 명령의 node 로)
   └─ 4. 1번 저장본에서 앱 전체 되살림
```

- 1번에서 **기존 저장본이 지금 목록으로 덮어써진다.** 재부팅 때 되살아날 목록도 함께 바뀌므로, 임시로 띄운 앱이 목록에 있으면 먼저 `pm2 delete`로 정리한다.
- 3번의 데몬 버전은 `pm2` 명령을 실행한 node가 정한다. 실행 전에 `pm2 report`의 `CLI` 칸 `node version`이 새 버전인지 본다.
- 부팅 자동 시작(`pm2 startup`)으로 등록해 둔 경우, 공식 문서는 Node를 올렸으면 `pm2 unstartup` → `pm2 startup`으로 다시 등록하라고 안내한다.

## 6. 경험과 교훈 / 트러블슈팅

### ❌ 서버 재부팅하니 앱이 다 사라짐

**원인**: `pm2 startup`만 하고 `pm2 save`를 안 했다. 부팅 시 pm2는 떴지만 복원할 목록이 비어 있었다.

**해결**: 앱을 원하는 상태로 띄운 뒤 `pm2 save`. 이후 목록이 바뀔 때마다 다시 `save`.

### ❌ 코드를 배포했는데 요청이 잠깐 끊김(reload인데)

**원인**: fork 모드(기본)라 프로세스가 1개뿐 → reload도 그 1개를 교체하며 순단.

**해결**: ecosystem에서 `exec_mode: "cluster"`로. 그래야 pm2가 새 인스턴스를 띄운 뒤 옛 것을 내리는 진짜 무중단이 된다(`instances: 1`이어도 됨 — 3장 함정 1). 단 교체 중 잠깐 두 프로세스가 함께 돌므로, 메모리에 상태를 들고 있거나 혼자만 돌아야 하는 작업(예약 작업 등)이 있는 앱은 먼저 확인한다.

### ❌ Node를 올렸는데 pm2 데몬은 옛 버전

**상황**: 서버의 node 실행 파일을 22.14.0 → 22.23.4로 교체했다. 다음 배포 뒤 확인하니 `pm2 describe my-api`의 `node.js version`은 22.23.4인데, `pm2 report`의 `Daemon` 칸 `node version`은 22.14.0이었다.

**원인**: 버전은 프로세스가 켜질 때 정해진다(5-1). 데몬은 교체 전에 켜져 옛 버전 그대로이고, my-api는 배포의 `pm2 reload`로 교체 뒤 다시 떠서 새 버전이 됐다.

**해결**: 앱은 이미 적용됐다. 데몬까지 올리려면 `pm2 update`(앱 전체가 다시 뜨므로 요청이 적은 시간에 — 5-3).

### ❌ PowerShell에서 `pm2 describe`를 `findstr`로 거르면 글자가 깨짐

**증상**: `pm2 describe my-api | findstr node.js`를 치면 표 테두리 문자(`│ ┌ ─`)가 `??`로 깨지고 줄이 엉켜 한 줄로 붙어 보인다. 영문·숫자는 남아 `node.js version ??22.23.4`처럼 읽히기는 한다.

**원인**: 표 테두리가 UTF-8 특수 문자라 `findstr`(오래된 Windows 명령)의 인코딩 처리와 맞지 않는 것으로 추정한다 — 원인은 확인하지 않았다.

**해결**: 필터 없이 표 전체를 보거나, PowerShell의 `Select-String`으로 거른다.

```powershell
pm2 describe my-api                              # 필터 없이 표 전체
pm2 describe my-api | Select-String "node.js"    # 필요한 줄만
```

## 7. Best Practices
- 운영 실행은 **ecosystem 파일**로 한다(옵션 직접 타이핑 금지 → 재현 가능).
- 무중단 배포는 **cluster 모드 + `pm2 reload`**.
- 서버 세팅 시 **`pm2 startup` + `pm2 save`**를 1회 해 재부팅에 대비한다.
- env를 바꿨으면 `--update-env`를 잊지 않는다.
- 잠깐 멈출 땐 `delete`가 아니라 `stop`(설정·로그 유지).
- Node를 올린 뒤엔 `pm2 describe`(앱)·`pm2 report`(데몬)로 실제 도는 버전을 확인한다 — 파일 교체만으로는 도는 프로세스가 바뀌지 않는다.
