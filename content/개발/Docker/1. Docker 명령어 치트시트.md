# 개요
> 실무에서 자주 쓰는 Docker 명령어만 워크플로우 순서로 추린 빠른 참조표. 개념 설명은 [[2. Docker 핵심 개념]]으로 분리한다.

---

## 1. 큰 그림 — 하루의 개발 사이클

명령어를 외우는 게 아니라 **흐름**으로 기억한다.

```
[코드 수정]
   │
   ▼
docker compose up -d ──► 실행 ──► docker compose logs -f ──► 문제 확인
                                        │
                        docker exec -it <c> bash ──► 컨테이너 안 들어가 조사
                                        │
   ┌────────────────────────────────────┘
   ▼
Dockerfile 바꿈? ──► docker compose up -d --build (다시 굽고 실행)
   │
   ▼
작업 끝 ──► docker compose down (─v 붙이면 볼륨=데이터까지 삭제)
```

---

## 2. 최신 주의 — `docker-compose`(하이픈)는 죽었다

| 구분 | 옛날 (v1) | 지금 (v2, 2026 표준) |
|---|---|---|
| 명령어 | `docker-compose`(하이픈) | `docker compose`(**스페이스**) |
| 정체 | 파이썬 별도 바이너리 | Docker CLI 내장 플러그인(Go) |
| 상태 | **2025-04 완전 제거** | 유일한 정답 |

> 옛 문서·블로그의 `docker-compose up`은 `docker compose up`으로 바꿔 읽는다. 이 노트는 전부 스페이스 버전.

## 3. 명령어 표 (그룹별)

### 3-1. Compose — 하루에도 몇 번씩

| 명령어 | 뜻 |
|---|---|
| `docker compose up -d` | 서비스 백그라운드 실행 (`-d` = detached, 터미널 점유 안 함) |
| `docker compose up -d --build` | 이미지 다시 굽고 실행 (**Dockerfile 바뀌었을 때만**) |
| `docker compose up -d <서비스>` | 특정 서비스만 실행 |
| `docker compose down` | 컨테이너·네트워크 정리 (이미지·볼륨은 유지) |
| `docker compose down -v` | + named volume까지 삭제 (**DB 데이터 날아감, 주의**) |
| `docker compose restart [서비스]` | 재시작 |
| `docker compose ps` | 이 compose가 띄운 것만 상태 확인 |
| `docker compose logs -f [서비스]` | 로그 실시간 (`-f` = follow) |

> **무엇을 고쳤을 때 무엇을 쓰나 — restart / up -d / --build**
>
> | 무엇을 고쳤나 | 명령어 | 무슨 일이 일어나나 |
> |---|---|---|
> | 마운트된 설정 파일 (예: `vhost.conf`) | `docker compose restart` | 같은 컨테이너를 껐다 켬 → 프로세스만 재시작. Apache 등은 시작 때 설정을 한 번 읽으므로 재시작해야 반영 |
> | `docker-compose.yml` (`ports`·`volumes`·`environment`) | `docker compose up -d` | compose.yml을 다시 읽어 컨테이너 **재생성** |
> | `Dockerfile` | `docker compose up -d --build` | 이미지부터 다시 굽고 → 재생성 |
>
> restart는 **compose.yml·이미지를 다시 읽지 않는다.** 프로세스 리부팅일 뿐. 볼륨 마운트로 코드가 실시간 반영되는 경우엔 restart조차 필요 없다.

### 3-2. 컨테이너 조작

| 명령어 | 뜻 |
|---|---|
| `docker ps` | 실행 중인 컨테이너 |
| `docker ps -a` | 멈춘 것 포함 전체 (`-a` = all) |
| `docker logs -f <컨테이너>` | 로그 실시간 |
| `docker exec -it <컨테이너> bash` | 컨테이너 안으로 진입 (`-it` = 대화형 터미널) |
| `docker stop <컨테이너>` | 멈추기 |
| `docker rm -f <컨테이너>` | 강제 삭제 (`-f` = 실행 중이어도) |

### 3-3. 이미지·빌드

| 명령어 | 뜻 |
|---|---|
| `docker images` | 로컬 이미지 목록 |
| `docker build -t 이름:태그 .` | Dockerfile로 이미지 굽기 (`.` = Dockerfile 위치) |
| `docker pull <이미지>` | 레지스트리에서 받기 |
| `docker rmi <이미지>` | 이미지 삭제 |

### 3-4. 정리 (디스크 확보)

| 명령어 | 뜻 |
|---|---|
| `docker system prune -a` | 안 쓰는 컨테이너·이미지·네트워크 일괄 삭제 |
| `docker volume ls` | 볼륨 목록 |
| `docker stats` | 컨테이너별 CPU·메모리 실시간 |

> **`docker system prune -a` 하나면 끝.** `docker rm $(docker ps -aq)` 같은 중첩 명령을 손으로 조합할 필요 없다.

## 4. 자주 쓰는 조합 흐름

```
# 완전 초기화 후 새로 (설정 꼬였을 때)
docker compose down -v  ──►  docker compose up -d --build

# 컨테이너 안에서 뭔가 확인
docker compose up -d  ──►  docker exec -it <c> bash  ──►  (내부) ls, cat, php -v ...

# 안 뜰 때 원인 추적
docker compose ps  ──►  docker compose logs -f <서비스>
```

---

## 5. 흔한 실수 / 함정

- **`down -v`의 `-v`** — 도커가 관리하는 **named volume**(DB 데이터 등)만 삭제한다. 마운트한 로컬 폴더(**bind mount**, 예: `./content`)는 안 건드리니 안전. "데이터 날림"은 named volume 얘기다. 볼륨 2종 상세는 [[4. Docker Compose]]. 데이터 유지하려면 `-v` 없이 `docker compose down`.
- **`--build`를 안 붙임** — Dockerfile을 고쳤는데 `up -d`만 하면 옛 이미지로 뜬다. Dockerfile·의존성 바뀌면 `--build`.
- **`docker ps`에 안 보임** — 멈춘 컨테이너는 `docker ps -a`로 봐야 나온다.
- **`stop` vs `rm`** — `stop`은 멈추기(재시작 가능), `rm`은 삭제(사라짐). `rm -f`는 멈춤+삭제 한 번에.
