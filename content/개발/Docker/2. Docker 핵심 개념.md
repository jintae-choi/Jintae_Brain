# 개요
> 도커의 4대 요소 — **이미지·컨테이너·레지스트리·볼륨** — 이 어떻게 연결되는지 멘탈 모델로 잡는다. 명령어는 [[1. Docker 명령어 치트시트]], 볼륨 상세는 [[4. Docker Compose]].

## 1. 전체 개념 / 흐름

### 1-1. 큰 그림 — Dockerfile에서 실행까지

도커가 푸는 문제는 **"내 PC에선 되는데 서버에선 안 돼"** 다. OS·라이브러리·버전이 달라서 생긴다. 해법은 실행 환경을 통째로 **이미지**로 굳혀서 어디서나 똑같이 실행하는 것.

```
[Dockerfile] ──build──► [이미지] ──run──► [컨테이너]
  설계도               금형(템플릿)       실행 중인 서버
                          ▲   │
                     pull │   │ push
                          │   ▼
                     [레지스트리]  ← Docker Hub 등, 이미지 공유 창고
```

핵심 성질: **이미지 1개로 컨테이너를 여러 개 찍어낼 수 있다.** (금형 하나로 붕어빵 여러 개)

### 1-2. 사전 지식 / 용어

- **이미지(image)** — 실행 환경을 굳힌 **읽기 전용 템플릿**. OS + 언어 + 설치된 패키지 + 설정이 한 덩어리.
- **컨테이너(container)** — 이미지를 **실행한 인스턴스**. 실제로 돌아가는 서버 하나.
- **레지스트리(registry)** — 이미지를 올려두고 받는 **원격 창고**. 대표: Docker Hub.
- **레이어(layer)** — 이미지는 여러 읽기 전용 **레이어의 겹**이다. `pull`은 파일 하나 다운로드가 아니라 **레이어들을 받아 쌓는 것**.
- **볼륨(volume)** — 컨테이너 **밖**에 데이터를 보관하는 장치. 상세는 [[4. Docker Compose]].

### 1-3. 비교 — 익숙한 것과 대조

**① 가상머신(VM) vs 컨테이너** — "격리된 실행 환경"이라 비슷해 보이지만 무게가 다르다.

| 항목 | 가상머신(VM) | 컨테이너 |
|---|---|---|
| 격리 방식 | 게스트 OS를 **통째로** 올림 | 호스트 커널을 **공유**, 프로세스만 격리 |
| 무게 | 무거움(GB, 부팅 수십 초~분) | 가벼움(MB, 기동 수 초) |
| 개수 | 한 PC에 몇 개 | 한 PC에 수십~수백 개 |

**② 금형 비유** — 가장 헷갈리는 이미지 vs 컨테이너.

| 비유 | 도커 | 성질 |
|---|---|---|
| **설계도** | Dockerfile | 고칠 수 있는 글 |
| 붕어빵 **틀** | 이미지 | 한 번 만들면 고정(불변), 여러 개 찍음 |
| 구워낸 **붕어빵** | 컨테이너 | 틀에서 나온 실체, 먹으면(삭제) 사라짐 |

설계도(Dockerfile)를 고치면 틀(이미지)을 **다시 만들어야** 한다 — 틀은 못 고친다.

### 1-4. 구성요소 역할

| 구성요소 | 역할 | 수명 |
|---|---|---|
| 이미지 | 실행 환경 템플릿(읽기 전용) | 빌드하면 고정 |
| 컨테이너 | 이미지를 실행한 서버 인스턴스 | 껐다 켜면(rm 후 재run) 새것 |
| 레지스트리 | 이미지 공유 창고(원격) | 영구(원격 보관) |
| 볼륨 | 데이터 영속 저장(컨테이너와 독립) | 컨테이너 지워도 유지 |

## 2. 오해 바로잡기

개념 노트라 "돌아가는 완성품 코드" 대신, 자주 틀리는 지점을 짚는다.

- **오해 — 이미지 = 파일 하나** — 아니다. `image.tar` 같은 단일 파일이 아니라 **레이어 묶음**이다. `docker images`로 보이는 건 로컬 스토어에 쌓인 레이어 집합.
- **`image: php:8.1-apache` 의 의미** — "PHP 8.1 + Apache가 **이미 설치된** 리눅스"를 즉시 생성. 내가 아무것도 안 깔아도 된다. 이 이미지는 누군가 `build` 후 `push`해 레지스트리에 올려둔 것.
- **`pull`은 파일 다운로드가 아니다** — 이미지 레이어를 네트워크로 받아 내부 스토리지에 쌓는 것. 이미 가진 레이어는 건너뛴다(캐시).
- **빌드된 이미지는 어디 있나** — 도커가 관리하는 **로컬 저장소**에 레이어 파일들로 이미 존재한다(Linux는 `/var/lib/docker`, Windows는 도커가 도는 WSL2 가상 디스크 안의 도커 영역). `docker images`가 그 목록. 다만 `.txt`처럼 열어보는 파일은 아니다(레이어 뭉치).
- **파일로 뽑기 — `docker save`** — `docker save img > img.tar`로 단일 tar로 export, `docker load < img.tar`로 복원. 폐쇄망 이전 같은 특수 상황용이라 **흔치 않다**: 보통은 (1) Dockerfile+코드를 git으로 공유해 각자 build하거나 (2) 레지스트리에서 pull하면 되고, 이미지 tar는 용량이 크고(수백 MB~GB) 바이너리라 손으로 옮길 일이 드물다.
- **GitHub 코드 저장소엔 안 올린다** — 용량 크고 바이너리라 부적합. 이미지는 **레지스트리**에 올린다: Docker Hub, 그리고 GitHub이 제공하는 컨테이너 레지스트리 **GHCR(`ghcr.io`)**. git 코드 저장소와는 별개의 "이미지 전용 창고".

## 3. 포인트 해설 — 이미지 태그 읽는 법

```
php : 8.1-apache
─┬─   ────┬─────
이름     태그(버전)
```

- **이름** — 이미지 종류 (`php`, `nginx`, `mysql`, `redis` …)
- **태그** — 버전·변형 (`8.1-apache`, `8.0-fpm`, `latest` …)
- **태그 생략 시 `latest`** — `docker pull nginx` = `nginx:latest`
- **실무는 버전 고정** — `latest`는 언제 다른 버전으로 바뀔지 모른다. `php:8.1-apache`처럼 **명시적 태그를 박아** 재현성을 지킨다.

---

## 4. 교훈
- **이미지는 "굽는 것"(build), 컨테이너는 "실행하는 것"(run).** 굽기는 [[3. Dockerfile]], 실행·묶기는 [[4. Docker Compose]]가 담당한다.
- **`latest` 대신 버전 태그를 고정한다.** 재현성이 도커의 존재 이유인데 `latest`는 그걸 깬다.
- **데이터는 컨테이너 안이 아니라 밖(볼륨)에 둔다.** 컨테이너는 언제든 지웠다 다시 만들 수 있는 일회용이라고 가정한다.
