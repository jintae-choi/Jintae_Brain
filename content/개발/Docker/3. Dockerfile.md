# 개요
> Dockerfile은 "이 서버를 이렇게 만들어라"를 적은 **설계도**다. 한 번 구워(build) 이미지로 고정하면, 이후엔 실행만 한다. 개념 배경은 [[2. Docker 핵심 개념]].

---

## 1. 전체 개념 / 흐름

### 1-1. 큰 그림 — 설계도에서 이미지까지

```
[Dockerfile] ──docker build──► [이미지] ──실행──► [컨테이너]
  설계도(코드)                  구워진 결과물
```

Dockerfile에 **모든 것을 코드로 고정**한다: OS 종류, 언어 버전, 설치 패키지, 설정 파일, 빌드 단계. 그래서 어떤 PC에서 구워도 같은 이미지가 나온다.

> **혼동 주의**: Dockerfile은 **이미지 파일이 아니다.**
> - `Dockerfile` → 이미지 생성 **규칙(설계도)**
> - `docker build` → 이미지 **생성 행위**
> - 생성 결과 → 도커 **이미지**

### 1-2. 사전 지식 / 용어

- **베이스 이미지** — `FROM php:8.1-apache`가 가리키는 건 **남이 구워 Docker Hub에 올린 완성 이미지**다(로컬에 없으면 거기서 `pull`). 그 위에 내 `RUN`·`COPY` 레이어를 얹어 **새 이미지**를 만든다 — 이미지 위에 이미지를 쌓는 구조. (이해를 돕자면 '바닥에 까는 재료'지만, 정확히는 그 자체가 하나의 이미지다.)
- **레이어(layer)** — Dockerfile의 명령어 **한 줄이 레이어 하나**를 만든다. 이미지는 이 레이어들의 겹.
- **빌드 컨텍스트** — `docker build .`의 `.` = Dockerfile과 함께 도커에 넘겨지는 폴더. 이 안의 파일만 `COPY` 가능.

### 1-3. 비교 — 왜 굽는가

**① 매번 설치 vs 미리 굽기**

도커를 처음 쓰면 "컨테이너 띄우고 그 안에서 설치"하기 쉽다. 하지만 컨테이너는 지우면 사라지므로 매번 반복된다. **Dockerfile로 한 번 구워두는 것**이 정답.

| 항목 | 매번 설치 (느린 구조) | 미리 굽기 (Dockerfile) |
|---|---|---|
| 흐름 | 컨테이너 실행 → apt 설치 → 확장 설치 → 설정 → 실행 | **빌드 때 1회** 설치 → 이미지 완성 → 컨테이너는 **실행만** |
| 재현성 | 사람마다·매번 다름 | 항상 동일 |
| 속도 | 띄울 때마다 설치 대기 | 즉시 기동 |
| 기록 | 머릿속·메모 | 코드로 남음 |

**② C 컴파일과 같은 구조 — build를 왜 하나**

빌드는 **C언어의 컴파일과 정확히 같은 구조**다.

```
C언어:   소스코드(.c) ──컴파일(gcc)──► 실행파일(.exe) ──실행──► 프로세스
Docker:  Dockerfile   ──빌드(build)──► 이미지          ──run──► 컨테이너
```

| C언어 | 도커 | 역할 |
|---|---|---|
| 소스코드(.c) | Dockerfile | 사람이 고치는 텍스트 |
| **컴파일(gcc)** | **빌드(build)** | 텍스트 → 실행 가능한 산출물로 변환 |
| 실행파일(.exe) | 이미지 | 완성된 **불변** 산출물 |
| 프로세스 | 컨테이너 | 산출물을 띄운 실행 인스턴스 |

`.c`를 실행할 때마다 컴파일하지 않듯, **미리 한 번 구워두면 컨테이너는 즉시 뜬다.** 그리고 `run`은 이미지가 있어야만 가능하다 — Dockerfile로 바로 컨테이너를 못 간다. build가 그 이미지를 만드는 필수 단계이고, compose의 `build:`는 build+run을 자동으로 이어줄 뿐 **내부적으론 반드시 이미지를 거친다.**

### 1-4. 주요 명령어(instruction) 역할

| 명령어 | 역할 |
|---|---|
| `FROM` | 베이스 이미지 지정(시작점) |
| `RUN` | 빌드 중 실행할 명령(패키지 설치 등) |
| `COPY` | 빌드 컨텍스트의 파일을 이미지 안으로 복사 |
| `WORKDIR` | 이후 명령의 작업 디렉터리 |
| `CMD` | 컨테이너가 **시작될 때** 실행할 기본 명령 |

## 2. 전체 예시 코드

```dockerfile title="Dockerfile"
# 1. 베이스: PHP 8.1 + Apache가 깔린 리눅스
FROM php:8.1-apache

# 2. Apache rewrite 모듈 켜기 + PHP 확장 설치 (빌드 때 1회)
RUN a2enmod rewrite \
 && docker-php-ext-install pdo_mysql

# 3. 소스 코드를 이미지 안으로 복사
COPY ./src /var/www/html

# 4. 컨테이너 시작 시 Apache를 포어그라운드로 실행
CMD ["apache2-foreground"]
```

빌드·실행:

```bash
# Dockerfile로 "환경이 고정된 이미지" 굽기
docker build -t myapp:local .

# 구운 이미지를 컨테이너로 실행
docker run -d -p 8080:80 --name myapp myapp:local
```

## 3. 라인별 해설

### 3-1. 빌드 명령

```bash
docker build -t myapp:local .
```

| 조각 | 뜻 |
|---|---|
| `docker build` | 이미지 생성 |
| `-t myapp:local` | 이미지 이름:태그 지정 (`-t` = tag) |
| `.` | Dockerfile이 있는 경로(=빌드 컨텍스트) |

> 실무에선 `:local` 대신 `:v1.0.0`처럼 버전 태그를 붙여 배포 이력을 남긴다.

### 3-2. Dockerfile 각 줄

- `FROM php:8.1-apache` — 남이 구운 "PHP+Apache 리눅스" 위에서 시작. 바닥을 직접 안 만든다.
- `RUN a2enmod rewrite && ...` — **빌드 시점에** 실행. 결과가 이미지에 구워져 컨테이너는 설치 없이 바로 뜬다.
- `COPY ./src /var/www/html` — 호스트의 `./src`를 이미지 안으로 복사. (실시간 반영이 필요하면 복사 대신 **볼륨 마운트** — [[4. Docker Compose]])
- `CMD ["apache2-foreground"]` — 컨테이너의 메인 프로세스. **포어그라운드로 떠야** 컨테이너가 유지된다(이유는 [[5. 컨테이너 생명주기]]).

## 4. 최신 포인트 — 레이어 캐시로 빌드 가속

Dockerfile 명령 **한 줄 = 레이어 하나**이고, 도커는 **바뀌지 않은 레이어를 캐시**한다. 위에서부터 순서대로 비교하다가, 바뀐 줄이 나오면 **그 줄부터 아래 전부**를 다시 빌드한다.

→ **자주 바뀌는 것(소스 코드)을 아래로, 잘 안 바뀌는 것(패키지 설치)을 위로** 두면 캐시가 살아 빌드가 빨라진다.

```dockerfile
FROM php:8.1-apache
RUN docker-php-ext-install pdo_mysql   # 거의 안 바뀜 → 위 (캐시 유지)
COPY ./src /var/www/html               # 자주 바뀜 → 아래 (이 줄만 다시)
```

- **`.dockerignore`** — `.git`, `node_modules` 등을 빌드 컨텍스트에서 제외해 빌드를 가볍고 안전하게. (`.gitignore`와 형식 같음)

---

## 5. 교훈
- **Dockerfile = 이미지 생성 규칙, 이미지 = 그 결과물.** 둘은 다르다. 빌드는 Dockerfile, 실행만 compose가 맡는다.
- **이미지는 불변이다.** 한 번 구우면 못 고친다. 바꾸려면 `Dockerfile 수정 → 다시 build → 새 이미지`. 옛 이미지를 편집하는 게 아니다.
- **"컨테이너 안에서 설치"하지 말고 Dockerfile에 굽는다.** 컨테이너는 일회용이라 설치가 매번 사라진다.
- **캐시가 살도록 명령 순서를 짠다.** 안 바뀌는 것 위, 자주 바뀌는 것 아래.
