## 개요
> 로컬 변경을 원격까지 안전하게 보내는 5단계 흐름(`stage → commit → fetch → merge → push`)과, `pull`이 `fetch + merge`로 쪼개지는 이유 정리.

---

## 1. 전체 개념 / 흐름

원격 저장소에 변경을 반영하기까지 코드는 4개의 "공간"을 순서대로 통과한다.

```
[Working Tree]   [Staging Area]   [Local Repo]   [Remote Repo]
   수정 중   ──►    커밋 대기실   ──►   로컬 이력  ◄──►   원격 이력
              add              commit         push
                                              ▲
                                              │
                                            fetch
                                              │
                                       [원격 추적 포인터]
                                       (origin/브랜치)
                                              │
                                            merge
                                              ▼
                                          내 브랜치
```

| 공간 | 역할 |
|---|---|
| Working Tree | 실제 파일 시스템. 편집기에서 보이는 그 파일들 |
| Staging Area | 다음 커밋에 포함할 변경만 모아두는 "대기실" |
| Local Repo | 내 PC에 영구 저장된 커밋 이력 (`.git/`) |
| Remote Repo | GitHub/회사 서버에 있는 공유 저장소 |
| 원격 추적 포인터 | 로컬에 캐시된 원격 상태 (`origin/브랜치`). 원격 자체가 아니라 "내가 마지막으로 본 원격" |

---

## 2. 사전 지식

흐름을 정확히 이해하려면 두 가지 개념부터 잡아야 한다.

### Staging Area (= Index)
모든 수정이 다음 커밋에 들어가는 게 아니다. `git add`로 명시적으로 올린 것만 커밋된다. 같은 파일이라도 일부 라인만 stage하는 것도 가능(`git add -p`). **선택권**을 주기 위한 중간 계층이다.

### 원격 추적 포인터 (Remote Tracking Branch)
`origin/main`은 원격에 직접 연결된 게 아니라, **로컬에 저장된 "원격이 이랬더라"는 스냅샷**이다. 네트워크 호출 없이 즉시 조회 가능하지만, 최신은 아닐 수 있다. `git fetch`가 이 스냅샷을 갱신하는 유일한 통로이다.

```
git fetch 전:                    git fetch 후:
origin/main → C2 (구버전)        origin/main → C5 (최신)
실제 원격   → C5                 실제 원격   → C5
```

## 3. 전체 예시 코드

`bcmf_s` 브랜치에 변경을 푸시하는 표준 시퀀스이다.

```bash
# 1. 변경한 파일 중 커밋에 넣을 것만 stage
git add src/components/Login.tsx

# 2. stage된 변경을 로컬 저장소에 커밋
git commit -m "feat: 로그인 폼 검증 추가"

# 3. 원격 최신 상태를 추적 포인터로 가져오기 (병합은 X)
git fetch origin bcmf_s

# 4. 원격이 앞서 있다면 내 브랜치에 병합
git merge origin/bcmf_s

# 5. 로컬 커밋을 원격으로 업로드
git push origin bcmf_s
```

## 4. 라인별 상세 해설

### 4-1. stage — `git add <파일>`

```bash
git add src/components/Login.tsx
```

- 커밋에 포함할 변경사항을 **커밋 대기실(staging area)**에 올리는 작업이다.
- 수정한 파일 중 이번 커밋에 넣을 것만 골라서 선택 가능하다.
- 파일 상태: `modified` → `staged`로 전환된다.

> **왜 이 단계가 따로 있는가?**
> 작업 중에는 보통 여러 파일을 동시에 건드린다. 그중 "이번 커밋"의 의미에 맞는 파일만 추려서 깔끔한 이력을 만들기 위한 장치이다. 한 번에 다 올리고 싶으면 `git add .` 또는 `git add -A`.

---

### 4-2. commit — `git commit -m "..."`

```bash
git commit -m "feat: 로그인 폼 검증 추가"
```

- staging area에 올린 변경사항을 **로컬 저장소에 영구 기록**한다.
- 커밋 해시(예: `3304cde...`)가 생성되고 `HEAD`가 이 커밋을 가리킨다.
- 이 시점에는 **아직 원격과 무관**하다. 내 PC에만 존재한다.

> **HEAD란?**
> "내가 지금 어느 커밋 위에 서 있는가"를 가리키는 포인터이다. 새 커밋을 만들면 HEAD가 자동으로 새 커밋으로 이동한다.

---

### 4-3. fetch — `git fetch origin bcmf_s`

```bash
git fetch origin bcmf_s
```

- 원격 저장소의 최신 상태를 **내 PC로 가져오기만** 한다.
- 내 작업 브랜치는 건드리지 않는다 — `origin/bcmf_s`라는 **원격 추적 포인터만 갱신**한다.
- "원격이 나보다 앞서있는지 먼저 확인하고 싶을 때" 안전하게 쓴다.

```
fetch 전:  내 브랜치 ─ C1 ─ C2 (HEAD)
           origin/bcmf_s ─ C1 (구버전 스냅샷)

fetch 후:  내 브랜치 ─ C1 ─ C2 (HEAD)         ← 그대로
           origin/bcmf_s ─ C1 ─ C3 ─ C4       ← 갱신됨
```

---

### 4-4. merge — `git merge origin/bcmf_s`

```bash
git merge origin/bcmf_s
```

- fetch로 가져온 원격 커밋을 **내 현재 브랜치에 합친다**.
- 독립적인 변경이면 자동 병합, 같은 라인을 건드렸으면 충돌 발생.
- `--no-ff` 옵션 — fast-forward 가능해도 병합 커밋을 명시적으로 남긴다. 협업 시 "여기서 합쳤다"는 흔적을 남기고 싶을 때 사용한다.

> **fast-forward란?**
> 내 브랜치가 원격보다 뒤처져 있고 그 사이에 내 새 커밋이 없으면, 병합 커밋 없이 단순히 HEAD를 앞으로 이동시키는 것. 이력이 깔끔해지지만 "병합했다"는 사실 자체는 사라진다.

---

### 4-5. push — `git push origin bcmf_s`

```bash
git push origin bcmf_s
```

- 내 로컬 커밋을 **원격 저장소로 업로드**한다.
- 원격이 나보다 앞서있으면 거부당한다 → 그래서 `fetch + merge`를 먼저 해야 한다.
- 거부됐을 때 `-f`로 강제 푸시하는 건 협업 브랜치에서는 금기. 다른 사람 커밋이 사라진다.

---

## 5. 경험과 교훈: pull은 어디 갔는가?

처음에는 "왜 흐름에 `pull`이 없지?" 싶은데, 사실 이미 들어 있다.

```
git pull = git fetch + git merge
```

`pull`은 두 단계를 한 방에 돌리는 단축 명령이다. 그러면 왜 굳이 쪼갰는가.

### ① 확인 후 판단
`fetch`만 하면 원격이 앞서있는지 먼저 볼 수 있다. 앞서있는 게 없으면 `merge` 자체를 건너뛰고 바로 푸시 가능하다. **불필요한 merge 커밋을 만들지 않을 권리**가 생긴다.

### ② 충돌 대비
`pull`로 한 방에 돌리다 충돌이 나면 "방금 뭐가 일어난 거지" 싶은 상태가 된다. `fetch / merge`를 쪼개면 "지금 내가 어느 단계에 있는가"가 명확하다. 충돌 해결도 의도적으로 진입하게 된다.

### ③ 로그 미리보기
fetch 후 아래처럼 원격이 들고 온 커밋을 먼저 본 다음 병합 여부를 결정할 수 있다.

```bash
git log HEAD..origin/bcmf_s   # 원격에만 있고 내겐 없는 커밋
git log origin/bcmf_s..HEAD   # 내겐 있고 원격엔 없는 커밋
```

### 요약표

| 명령 | 하는 일 | 제어권 |
|---|---|---|
| `git fetch` | 원격 → 로컬 추적 포인터만 갱신 (안전) | 높음 |
| `git merge` | 추적 포인터 → 내 브랜치로 병합 | 높음 |
| `git pull` | 위 둘을 한 방에 | 낮음 (편함) |

`/ship` 플로우처럼 **자동 배포** 중간에 판단 포인트가 필요한 상황에서는 `fetch / merge`로 쪼개는 게 안전하다. 평소 혼자 작업하는 브랜치에서는 `git pull`로 줄여도 무방하다.
